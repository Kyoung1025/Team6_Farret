## 6. 시나리오 3A — AWS Auto Scaling 부하 실험 (2026-10-21)

### 6.1 실험 방법

- **시간:** 2026-10-21 **11:05~11:40경** KST.
- **본인 수행:** AWS CloudShell에서 `hey`로 ALB에 HTTP 부하 주입; Ubuntu VM에서 Grafana와 별도 `curl` 로그인 페이지 검사 기록 및 비교.
- **팀원 검증:** AWS CloudWatch·ASG·Target Group에서 CPU/인스턴스/Healthy 변화 관찰.
- **테스트 단계:** `c20 / 120초`, `c100 / 약 300초`. `-c`는 **총 요청 수**가 아닌 **동시에 진행할 최대 요청 수**.

### 6.2 `hey` 실측

| 지표 | c20 / 120초 | c100 / 약 300초 |
|---|---:|---:|
| 완료된 HTTP 200 | **14,955** | **37,244** |
| hey가 보고한 오류 | 0 | 0 |
| 평균 처리량 | **124.53 RPS** | **120.45 RPS** |
| 평균 응답시간 | **0.1605초** | **0.8256초** |
| p95 | **0.1324초** | **0.9395초** |
| p99 | **0.3817초** | **13.9016초** |

- 전체 완료 HTTP 200 **52,199건(14,955+37,244)**. **hey가 완료해 응답 받은 요청에 한정한 수치**이며 모든 실제 사용자 기능이 항상 성공했다는 뜻은 아니다.
- AWS 앱 EC2 CPU **거의 100%**로 상승, ASG 인스턴스 **1→2**, 앱 TG Healthy **2개** 등록을 관찰해 확장 동작을 확인.
- c100에서 평균 처리량은 c20과 비슷했지만 응답 지연이 커졌음. **확장 동작 성공과 전체 서비스 성능 개선은 별도로 평가**해야 한다.
- Grafana Blackbox의 `/healthcheck/` 경로는 실험에서 UP을 유지한 구간이 있었으나, Ubuntu에서 별도로 수행한 **`/control/login` curl 검사**는 441회 중 **HTTP 200 405회, HTTP 응답 미수신(`000`) 36회**가 기록됨. `000`은 HTTP 상태 코드가 아니며, 경로·타임아웃·관측 지점이 다른 검사와 오류율을 섞어 해석하지 않는다.
- **2026-10-25에야 Grafana CloudWatch 연동 완료.** 10월 21일 당시 AWS CPU·ASG 근거는 CloudWatch/ASG 콘솔 확인이며, 이후에 같은 종류의 지표를 Grafana로 통합했다.

### 6.3 검증할 때 비교할 지표

1. `hey`: 요청 수, HTTP 코드, 처리량(RPS), 평균·p95·p99 지연.
2. `CloudWatch`: EC2 CPU, `GroupDesiredCapacity`, `GroupInServiceInstances`, 앱 TG `HealthyHostCount`.
3. `Grafana`: Blackbox `probe_success`, 검사시간, Rocky/WG 수집 지표(각 지표가 실제 대상에 해당하는 경우).
4. `curl`: `/control/login` HTTP 200/응답 미수신 수를 별도 집계.
