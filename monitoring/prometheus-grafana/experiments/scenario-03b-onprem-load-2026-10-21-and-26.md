## 7. 시나리오 3B — 온프렘 Pretix 부하·재검증

### 7.1 1차 실험: 2026-10-21 단계별 부하

동료의 단계별 `hey` 실험 결과를 본인이 Grafana Nginx·Rocky·k3s 관측과 교차 비교했다. 1차 실험 경로/기준 조건에 대한 확인이 충분하지 않아 **최대 안정 처리량을 확정하지 않는다.**

| 동시 요청 수 | 1차 기록 평균 RPS | 기록 오류율 |
|---|---:|---:|
| c5 | **36.57** | **0.21%** |
| c10 | **52.15** | **0%** |
| c20 | **25.00** | **1.21%** |
| c30 | 원본 hey 결과 미확보 | 원본 미확보 |

- c20에서 RPS 하락과 오류율 **1.21%**, c40에서 RPS 재상승으로 결과가 단조롭지 않았다.
- Grafana에서 **c40 전후 Nginx RPS 순간 최고 약 86.79 req/s**, 활성 연결 최대 약 **48개**를 관측. `hey c40의 평균 61.36 RPS`와 `Grafana Nginx 순간 최대 86.79 req/s`는 **측정 주기·지점이 다른 값**이다.

- 61.36 RPS를 Pretix의 한계치나 일정 오류율 이하의 **안정적 최대 성능**으로 표현하지 않는다.

### 7.2 직접 경로 재검증: 2026-10-26

**목적 변경:** 기존 ALB 경유 실험의 변수와 구분하기 위해 Ubuntu→WG→Rocky 앱 NodePort **직접 접속**을 우선 검증. CPU 포화로 본격 고부하는 진행하지 않음.

```text
Ubuntu Monitoring (192.0.2.3)
   → AWS WireGuard Hub (192.0.2.1)
   → Rocky Linux (192.0.2.2:30637)
   → k3s Nginx NodePort → Pretix
```

**트러블슈팅:**

1. 최초 Ubuntu→`192.0.2.2:30637` 통신이 타임아웃.
2. WireGuard handshake와 다른 모니터링 포트는 정상이었으므로, VPN 전체 고장으로 단정하지 않음.
3. AWS WG 허브의 iptables **FORWARD DROP 규칙이 TCP 30637 경로를 차단**한 것을 확인.
4. 차단 규칙보다 앞에서 `192.0.2.3 → 192.0.2.2 TCP/30637`, `wg0 → wg0`만 제한적으로 허용하는 ACCEPT 규칙을 반영.
5. 해당 허용 규칙 카운터가 **0→9 packets**로 증가하는 것과 직접 HTTP 응답을 확인.
6. 팀 공용 허브 방화벽 변경이므로 **영구 유지/원복 여부 및 정책 반영**은 팀 운영 절차에 따로 확인 필요.

**당시 수행한 `hey` 예비 테스트 명령:**

```bash
export TARGET_URL='http://192.0.2.2:30637/'
mkdir -p ~/ferrot-3b-results
cd ~/ferrot-3b-results
hey -z 20s -c 2 -t 15 "$TARGET_URL" 2>&1 | tee public-results-summary.md
```

**중단 근거:**

- Rocky는 **2 vCPU·약 3.5GiB 인식 메모리**의 제한된 VM.
- 테스트 전후 CPU 사용률 **약 99.3% / CPU idle 0~1%**, Load Average 약 **10~11**, 실행 대기 태스크 다수.
- 메모리 약 **78.6~80%**, Swap 일부 사용(약 345~350MiB) 관측. **Swap이 실제 병목 원인이라고 확정하지 않음.**
- k3s 관리 계층의 housekeeping 지연 및 API timeout 기록. CPU 포화와 서비스 위험을 우선 고려.
- **c5 이상 부하는 2026-10-26 재검증 회차에서 시행하지 않았다.** c2 80/80 성공은 저부하 연결·기능 확인일 뿐 안정적 최대 성능의 근거가 아니다.
- 10월 21일 c40과 10월 26일 c2는 **날짜·접속 경로·서버 상태가 다르므로 수치 직접 비교 금지**.
